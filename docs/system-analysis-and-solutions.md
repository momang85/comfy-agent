## 一、从错误反推的系统特点（架构画像）

### 特点 1：三层结构没问题，**层间契约没有单一事实源**
系统分三层：大脑（LLM 决策）→ 引擎（确定性渲染/校验/修复）→ ComfyUI（外部契约）。
本次所有阻断性故障都**不在层内，而在层与层的接缝**：

| 契约对象 | 引擎侧的形态 | 对端实际要求 | 后果 |
|---|---|---|---|
| 模型文件名 | 模板默认 `sdXL/nova`、校验归一化、修复再产出归一形式 | ComfyUI 枚举的**精确字符串** `sdXL\nova` | 每任务失败 2-4 次；两个模板彻底不可用 |
| 视频节点类 | OOM 修复只认 `EmptyLatent*` | 视频用 `MiniMaxH3ImageToVideo` 等 | OOM 时无自动降参 |
| 视频文件位置 | 模板假定文件已在 `/input` | 需先上传 | 取帧/合并类任务失败 |
| 启动显存模式 | 脚本写死 `--highvram` | 19.5GB 模型需动态显存 | ComfyUI 硬崩溃 |

→ **同一个事实（模型名、节点类、文件位置、显存策略）在系统里有多个副本，且没有一处是权威的。**

### 特点 2：大脑是"概率性执行者"，但**前置条件没有被引擎强制**
本次大脑的典型偏差：漏步骤（忘了先上传视频）、编参数（`dpmpp_2m_karras`）、
改语义（"放大"→重新生成）、自我否定（引擎 9/10，它自己判 6/10 后重做）。
引擎对这些**只在提交瞬间才暴露**（服务器 400 / 连不上），且修复回路会**放大**错误
（归一化建议 → 写回 → 再被拒）。→ 前置条件应当是引擎强制的**不变量**，而不是大脑的记忆负担。

### 特点 3：评估是**双轨制且无仲裁**
引擎强制评估（通用 criteria，实测三段全部 9/10 通过）与大脑 `view_video`（任务 criteria，6/4/5 不通过）
对**同一个产物**给出相反结论，且无人仲裁 → 大脑按低分盲目重生成 **3 段视频（≈18 分钟 GPU）**，
最后撞上执行上限，向用户交付"视频是静态图、失败"的结论。→ 缺"权威结论"与去重。

### 特点 4：恢复力**只覆盖参数层，不覆盖进程/环境层**
参数级失败有完善的自动修复（枚举/范围/文件/结构级 VAE），而 ComfyUI 进程被大模型拖崩时，
引擎只能报"连不上…请先通过绘世启动器启动"——这个建议大脑无法执行，用户也只得到转述。
`repair.py` 建议的 `run_lowvram.bat` 在仓库里根本不存在。

### 特点 5：可观测性不足
5-15 分钟渲染期前端只有"阶段: running / 队列 1"；警告文本会**覆盖**阶段显示；
启动脚本用 `>` 截断日志（崩溃现场重启即失）；`webui.pid` 不校验就去 `taskkill`。

### 特点 6：**环境假设被写进启动脚本**，且与任务类型冲突
`--highvram`（图像场景的提速优化）对视频任务致命；`--normalvram` 已从 ComfyUI 移除但仍在 usage 文本里。

## 二、针对性解决方案

### P0-1 模型名单一事实源（修阻断）
- 新增 `model_adapt.resolve_canonical(knowledge, name) -> str|None`：把请求名与 `/models` 清单做
  **分隔符归一后的精确匹配**，返回**清单里的原始字符串**
- `adapt_ckpt()` 用它覆盖 `params["ckpt"]`；`checkpoint_exists()` 改为返回 canonical 名
- `validate.py` 的建议值用原始 `choices[idx]`，**绝不用归一化副本**；分隔符不一致产出 warning
- 验收：项目 A 四项各一次通过（A3/A4 不再失败）

### P0-2 启动脚本显存策略（修崩溃）
- `一键启动.bat` **默认不加 `--highvram`**（12GB 卡跑 19.5GB 模型的唯一可行路径）
- 另给 `一键启动_高显存.bat`（仅图像场景用），README 注明"视频任务勿用 --highvram"
- 验收：启动脚本起服务后跑 5 秒视频不再崩

### P0-3 前置条件不变量：**上传由引擎负责**（修"漏步骤"类失败）
- 模板声明 `requires_input_files`（extract_frame/merge_videos 的 video、i2i/i2v 的 image）
- `runner.run_template` 在渲染前检查：若值指向本机文件而目标不在 `/input`，**自动 upload**
  （`client.upload_image` 已支持任意文件）
- 验收：B2（取末帧）与 B4（合并）由大脑自由表述也能一次通过

### P1-1 评估仲裁与统一
- 引擎评估事件带 `prompt_id` 与 **criteria 由任务提示词生成**（不再是通用文案）
- `view_image`/`view_video` 先查"本轮是否已评估且通过"→ 已通过则跳过（或仅做抽检）
- 验收：一段视频只生成 1 次、只出现 1 张评估卡

### P1-2 枚举修复回落"模板推荐值"
- `repair._fix_issue` 的 `bad_enum` 分支：优先用模板 `Param.default/recommended`，
  其次 `choices` 首选，最后才用字符串相似度
- 验收：`dpmpp_2m_karras` → `dpmpp_2m`（而非 `dpmpp_2m_sde`）

### P1-3 进程级自愈 + 死引用清理
- 引擎侧：检测到 ComfyUI 不在 → ① 若 `comfy_root.local` 存在，提供 `cli start-comfy` 主动拉起；
  ② 否则给出**可执行**的中文指引（而不是"通过绘世启动器"）
- 删除 `repair.py:236` 对不存在的 `run_lowvram.bat` 的引用，改指向真实路径/说明

### P1-4 视频 OOM 降参
- `suggest_for_execution_error` 覆盖 `MiniMaxH3ImageToVideo` / `EmptyMiniMaxH3LatentAV` / `LTXVImgToVideo`
  的 `width/height/length`（按 0.6 系数降），并联动提示"帧数减半"

### P1-5 音频要么补、要么别说
- 补：接 H3 音频解码 + `CreateVideo` 的音频输入；
- 或明确：模板描述去掉"音画同生"，README 注明当前仅视频轨

### P2 可观测性与运维
- 渲染期进度：轮询 ComfyUI 执行进度（或 ws `progress`），转 `progress` 事件；前端显示"第 n/m 步"
- 警告走独立区域，不覆盖 `#statusline`
- 评估卡按 `prompt_id` 去重
- 启动脚本：日志改追加（`>>` 或按时间戳轮转）、`webui.pid` 校验后再 kill、`AGENT_HOME` 规范化为绝对路径

## 三、硬件安全（本次实测结论，务必保留）

**实测数据**：视频渲染期间 GPU **82-84°C / 100% / 8-10GB 显存**；执行 `/api/interrupt` 后
**12 秒**内降到 66°C、显存回落到 1.1GB（模型卸载）。空闲 53°C。

**危险组合**：`--highvram` + 19.95GB 的 H3 INT8 权重 → 直接 `access violation`（不是可恢复 OOM）。

**建议固化为默认策略**：
1. 启动默认动态显存（P0-2）；大模型任务杜绝 `--highvram`
2. 引擎侧加**温度熔断**：复用 `scripts/run_complex_task.py` 已有的 `nvidia-smi` 轮询机制，
   阈值建议 85°C → 自动 `interrupt` + 事件告知（本次是人工盯守 + 手动中断）
3. 任务间留冷却窗口；**尤其要禁止"因评估冲突而重复渲染"**（本次白烧 3 段 ≈18 分钟满载）
4. 前端已有显存仪表，建议再加温度（渲染期唯一可见的硬件指标）

**本次测试期间的自我保护**：温度 ≥82°C 时人工中断了 1 次错误渲染；全程未出现 ≥85°C。
